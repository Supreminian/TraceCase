## 1. 背景与目标

从 PRD 自动生成测试用例容易出现三类问题：遗漏业务规则与边界、把未说明的规则当成事实、无法解释用例来源与审核过程。本项目通过保留需求段落引用、校验结构化输出、人工逐条审核和保存版本事件，验证一条可检查、可回溯的生成流程。

用户输入 Markdown PRD 后，系统提取功能、角色、业务规则和待澄清项，生成测试用例草稿；审核人处理歧义并逐条通过、退回或修改；满足导出条件后，系统生成 CSV 或 Markdown 测试表，同时保存本次输入、生成和审批记录。

首版成功的标志：

1. 用固定样例完整演示“输入 → 生成 → 校验 → 审核 → 导出 → 查询历史”。
2. 每个用例可追溯到输入段落，每次审批可定位到具体用例版本。
3. 对含糊、缺角色、冲突阈值的输入能展示待澄清项，缺失信息不能被静默补齐。
4. 未通过、已退回或修改后待审的当前版本不能导出为批准版本。
5. 建立冻结的评测标准和原始结果记录方式，后续用真实结果比较 Prompt V1/V2。

系统不声称符合金融监管标准，也不定位为企业级合规平台。模型能否可靠识别歧义、覆盖需求，应由后续评测验证，不作为预设结论。

## 2. 范围与角色

### 2.1 首版范围

- 单人、单机使用的 Streamlit 页面；本地 SQLite 持久化。
- Markdown 上传或直接粘贴，段落编号与输入快照。
- 可替换模型适配器；先实现固定样例，再接入一种实际模型服务。
- 结构化提取、测试用例生成、Pydantic 校验与校验错误展示。
- 逐条审核、用例修订、审批事件、运行详情与历史查询。
- 满足门禁后的 CSV / Markdown 导出。
- 20 份小型 PRD 的评测数据、标注规范和执行方式。
- 基础单元测试与 CI；开发阶段使用 GitHub Issue → 分支 → 提交 → PR。

### 2.2 不在首版范围

- 真实报销、支付、发票核验或金融系统对接。
- 生产个人信息、真实金融数据、OCR、PDF/Word 输入。
- SSO、组织权限、多租户、多人实时协作、电子签名或监管审计认证。
- 自动执行测试、自动修改业务系统、自动批准用例。
- 多代理编排、向量检索、模型微调、复杂仪表盘与正式成本结算。
- 批准用例子集的部分导出、未批准草稿的文件导出。

### 2.3 使用者

| 产品角色 | 职责 | 首版处理 |
| --- | --- | --- |
| 生成发起人 | 输入 PRD，查看提取和生成结果 | 与审核人可为同一人 |
| 审核人 | 检查引用和业务依据，逐条通过、退回、修改 | 操作者标识必填；不做身份认证 |
| 评测者 | 标注标准、判定质量、分析错误 | 使用独立评测记录 |

以上为产品使用角色。PRD 中的申请人、审批人等是业务角色，两者不混用。缺失的业务角色必须列入澄清项；不能因产品存在“审核人”就补出业务审批人。

## 3. 用户流程与页面

1. **新建运行**：输入操作者标识，选择固定样例或模型模式，粘贴/上传 PRD，查看输入限制和模式说明。
2. **检查输入**：校验格式与长度，展示带段落 ID 的原文预览；开始生成前固定输入快照。
3. **生成与校验**：保存运行配置，调用适配器，保留原始返回，再进行 JSON、Schema 和引用校验。
4. **查看结果**：并列查看需求段落、提取结果、澄清项和测试用例；点击引用定位原文。
5. **逐条复核**：通过、退回或修改用例。页面显示当前版本、状态、操作者及历史记录。
6. **处理歧义**：需要新增/修改业务事实时，补充 PRD 后创建关联的新运行；保留旧运行，新运行重新审核。
7. **导出与追溯**：满足全部门禁后导出，记录导出快照；在历史页按运行 ID 查询输入、原始输出、修订和审批事件。

首版设置三个主要页面：新建运行、运行详情与审核、运行历史。评测先采用本地命令或脚本，不要求另建评测 UI。

## 4. 输入与需求追溯

### REQ-IN-01：输入限制

- 支持粘贴 Markdown，或上传单个 UTF-8 编码的 `.md` / `.markdown` 文件；不允许两种来源同时生效。
- 拟定限制：文件最大 100 KiB（102,400 字节）；规范化后正文最多 20,000 个 Unicode 字符。上传同时检查两项，粘贴检查字符数。
- 拒绝空白输入、不支持的扩展名、非 UTF-8 内容、NUL 字符及超限输入；提示原因，不调用模型。
- 扩展名不能代替内容检查；允许普通纯文本作为 Markdown 正文。
- 页面明确要求使用虚构数据。首版不承诺自动识别或脱敏所有真实个人数据。

### REQ-IN-02：原文与段落 ID

- 保留原始输入及规范化文本；规范化仅处理 UTF-8 BOM 和换行符，不改写业务内容。
- 按 Markdown 顶层内容块分配 `P001`、`P002` 等 ID，保存原文、类型及起止行号。标题、正文、列表、表格和代码块保留边界；一个列表或表格可作为一个引用块。
- 同一输入快照的编号固定。段落 ID 仅在所属运行内唯一，完整定位为 `run_id + paragraph_id`。
- 修改 PRD 后创建新运行，重新编号并通过 `parent_run_id` 关联；旧编号不跨运行自动复用。
- 输入摘要为确定性预览：标题、字数和正文前 200 字；另外保存完整输入的 SHA-256。摘要不代替全文，哈希不代表防篡改认证。

### REQ-EXT-01：提取内容

输出包含功能、业务角色、业务规则和待澄清项。功能、角色、规则均有唯一 ID 和一个以上来源段落；角色的职责仅可来自明确原文，未说明时保留缺失状态。

业务规则区分 `clear`、`ambiguous`、`conflicting`、`incomplete`。每个澄清项记录问题、涉及段落、关联规则、影响的用例以及是否阻断批准。

- 能影响前置条件、执行动作、预期、权限或覆盖判定的未知信息，默认阻断。
- 不影响测试执行或判断的文字建议可以为非阻断项；必须说明依据。
- 无法归属于局部规则的阻断问题标记为影响整次运行。
- 模型给出的“已识别歧义”不是完整性保证，审核人可以补充澄清项并阻止导出。

## 5. 生成结果与校验

### REQ-GEN-01：用例字段

| 字段 | 含义与约束 |
| --- | --- |
| `case_id` | 运行内唯一编号，如 `TC-001` |
| `title` | 可读的测试名称，不能为空 |
| `requirement_ids` | 关联规则 ID，至少一项 |
| `paragraph_ids` | 来源段落 ID，至少一项 |
| `preconditions` | 前置条件数组；可执行用例须完整，未知条件不能伪装成已知 |
| `steps` | 有序步骤，每项含连续序号及动作 |
| `expected_results` | 可观察、可判断的预期数组 |
| `priority` | `P0` / `P1` / `P2`，表示测试建议优先级，不代表原文规定 |
| `category` | `normal` / `boundary` / `exception`，一个主要分类 |
| `readiness` | `ready` / `needs_clarification` |
| `clarification_ids` | 阻断该用例的澄清项；待澄清用例至少关联一项 |

优先级建议：P0 为主要流程或重要业务约束，P1 为一般边界与异常，P2 为辅助场景；审核人可调整。不对分类数量设硬配额，避免为凑齐分类编造规则。

业务角色、金额精度、审批顺序、重复发票的范围、错误提示文案等，只有原文明示时才能作为已确定规则。原文没有 UI 或接口细节时，用例描述业务动作，不虚构按钮名称、接口地址或 HTTP 状态码。

信息不完整时可以保留待澄清用例草稿，明确未知部分；这类用例不得通过审核或进入批准导出。模型不需要为每个不明确规则强行产出完整用例，但必须保留该规则和阻断性问题。

### REQ-GEN-02：输出约定

模型适配器返回原始响应、模型元数据、用量（可选）及计时信息。业务 JSON 顶层包含：

```text
schema_version
features[]         -> id, description, paragraph_ids[]
roles[]            -> id, name, responsibilities[], paragraph_ids[]
business_rules[]   -> id, statement, status, paragraph_ids[]
clarifications[]   -> id, question, paragraph_ids[], requirement_ids[],
                      affected_case_ids[], scope, blocking
test_cases[]       -> REQ-GEN-01 中的字段
```

运行 ID、审核状态、操作者、时间和用例版本由应用管理，模型无权填写或批准。若模型输出额外的审批字段，按不允许的字段处理。

### REQ-VAL-01：分层校验

1. **JSON 解析**：完整响应必须能解析成单一 JSON 对象；Markdown 代码围栏、解释性前后缀不算严格 JSON 合法。
2. **Schema 校验**：检查类型、必填字段、枚举、数组和字符串约束，禁止未知字段。
3. **一致性校验**：ID 唯一，引用存在，步骤连续，关联段落覆盖所引用规则的来源；澄清项与待澄清状态一致；明确规则不能完全没有关联用例。
4. **人工语义校验**：引用是否真正支持预期、是否遗漏权限与边界、是否出现无依据规则、用例是否可执行。

前三层为程序检查，第四层依赖人工及评测。Schema 合格不等于业务正确，引用存在不等于引用支持结论。

硬性校验失败时保存原始输出与定位信息，展示字段路径和失败原因；不进入正常审批，也不导出批准版本。不静默改写业务事实、裁剪或自动重试。再次生成创建新的关联运行，保留失败记录。

2026-10-27 用户体验修订：用户无需为内部模型输出格式修改 PRD。用例、澄清问题无需重复列出关联规则的全部段落；直接来源和经规则关联的补充来源在界面区分展示，缺少重复来源仅提示人工核对。系统根据已声明的阻断问题计算 `clarification_ids` 和 `readiness`，保存整理前后差异及策略版本；不修改业务规则、步骤、预期或原始响应。模型标记待澄清却没有说明问题时，增加一个仅影响该用例的人工核对问题，不能静默改为就绪。无法解析、非法字段类型、悬空引用和重复 ID 仍为硬错误。

完整 JSON 的历史失败结果支持不调用模型的本地重新校验，创建关联新运行，保留原始输出、原模型配置及旧校验记录；新用例全部待审核。源文档不足通过澄清问题表达，不以“全部重复填写来源段落”等实现细节阻断正常审核。批准与导出门禁不变。

### REQ-GEN-03：固定样例与真实模型

- 默认使用固定样例模式，界面标识“固定样例，未调用模型”；配置和结果中记录 `provider=fixture`。
- 固定样例通过输入快照哈希匹配预置结果，包含正常、歧义、冲突和非法输出等情形。未匹配的自定义 PRD 提示不支持，不返回一个看似针对该输入的通用答案。
- 适配器可替换为实际模型；密钥从环境变量读取，不写入 PRD、SQLite、日志或导出文件。
- 实际服务商、模型、超时与输出上限、价格来源和预算在接入时确定。未配置成功前禁用实际模型调用。
- 保存模型名称、服务商、参数、可取得的模型修订标识、Prompt 版本、模板全文/哈希、完整渲染后的请求内容和 Schema 版本；请求不含认证头或密钥。
- PRD 作为待分析资料传入，不能覆盖系统生成约束；原文中的“忽略规则、自动批准”等内容不能触发操作。

## 6. 人工审核与版本

### REQ-REV-01：逐条操作

| 操作 | 条件 | 结果 |
| --- | --- | --- |
| 通过 | 当前用例可执行、引用有效、无关联阻断问题，审核人确认内容有依据 | 当前版本记为 `approved` |
| 退回 | 提交退回理由 | 当前版本记为 `returned`，阻止批准导出 |
| 修改 | 编辑标题、引用、前置、步骤、预期、优先级或分类，提交修改理由，保存前重新校验 | 创建下一版本，状态为 `pending_review` |

首版不提供批量自动通过、用例删除或“忽略该用例后继续导出”。若生成了不必要或无依据的用例，可退回并在关联新运行中重新生成；原记录保留。

已通过的版本允许退回；误操作也通过追加事件纠正。已退回版本不能直接再次通过，必须先提交新修订。所有内容修改，包括文字或优先级调整，都产生新版本并重新审核。

### REQ-REV-02：事件记录

- 生成用例初始版本为 v1，修订后递增；版本内容不可覆盖。
- 每次操作记录：事件 ID、运行 ID、用例 ID、目标版本、动作、操作者标识、服务端时间、理由、操作前后状态；修订还记录前后版本关系。
- 操作者标识长度拟定为 1–64 个字符，去除首尾空白；通过时可从下拉框选择说明，默认“通过，无需补充说明”，无需输入文字；选择“其他”时填写补充说明。事件记录所选说明，不自动声称完成额外检查；退回和修改必须填写具体理由。
- 时间以 UTC 存储，页面以 Asia/Shanghai 显示并注明时区。
- 新版本保存与事件写入必须处于同一数据库事务；任一失败则不改变当前版本。
- 操作提交时校验预期版本和当前状态；旧页面提交不得覆盖新版本，应提示刷新。

操作者标识为使用者自报标签，不是已认证身份。SQLite 历史用于学习验证，不保证对具有本地数据库写权限的人防篡改。

### REQ-REV-03：澄清与重新生成

- 审核人可新增澄清项，立即重新计算相关用例和整次运行的导出资格。
- 补充角色、阈值、权限等业务事实必须写入修订后的 PRD，创建带 `parent_run_id` 的新运行；新事实具有新运行中的段落引用。
- 若原文已足够、模型误报歧义，可追加“澄清误报”事件，填写原因和支持段落；受影响用例必须建立新版本、重新审核。原问题不得删除。
- 处理误报后的新版本依据当前问题状态更新 `clarification_ids`；关联阻断已解除且必要内容补齐、校验合格后，由审核人确认可执行，系统更新 `readiness` 并保存为待审核。不能独立编辑这两个字段来跳过问题处理；“保存修订”和“通过”仍为两个动作。
- 不能只把 `blocking` 改成 `false` 来绕过问题。将问题认定为非阻断同样需要追加理由及依据，并为受影响用例建立新版本、重新审核。
- 跨运行不自动继承审批；新运行所有用例从 v1、待审核开始。

### REQ-REV-04：状态规则

生成状态单独记录为：`created → generating → valid / invalid / failed`；进程中断后，未完成运行应可识别为失败/中断并保留上下文。

单条用例版本的审核状态为：`pending_review / approved / returned`。业务信息是否完整由 `readiness` 表达，避免混用生成状态和审批状态。

整次运行的“待审核 / 有退回 / 有阻断 / 可导出”由当前版本及澄清项动态计算，不由模型或用户直接设置。一个运行可以导出多次，每次导出都是独立快照。

### REQ-REV-05：审核完成与迭代（2026-10-27 补充）

- 审核完成是所有当前用例均不再待审，不等同于批准通过。页面必须持久展示本轮结果与下一步。
- 全部通过且完整导出门禁满足时，自动导航到导出页；导航本身不生成或下载文件。
- 有退回项时，自动导航到审核结果，汇总当前版本的退回原因，提供人工修订和模型修订；仍有待审项时先完成本轮。
- 人工修订沿用原运行，逐条创建新版本并复审，不改动其他用例的批准记录。
- 模型修订携带原需求、当前有效结果、源运行修订号、退回事件与理由，使用独立 REVIEW-R1 Prompt。只允许修改退回用例，保持用例编号/集合、已通过内容及提取结果不变；服务层拒绝越界输出，保留原始响应。
- 模型修订创建关联新运行，所有用例重新待审，不继承审批。源运行保留新增的迭代发起事件，新运行保存确切输入快照和反馈，不覆盖原版本。
- 退回意见若涉及新增业务事实，先修订 PRD 再生成；反馈不代替原文。Schema 与内容锁不能证明语义有依据，仍需人工复核。
- 修订失败时可返回上一轮继续处理；不自动重试。退回用例没有改动时明确提示用户核对，不自动视为修复成功。
- 模型修订仅由显式提交触发；固定样例不充当修订引擎。修订流程与正式 V1/V2 评测分开记录。

## 7. 批准导出与历史

### REQ-EXP-01：整次运行门禁

首版仅提供“导出批准版本”，必须同时满足：

1. 运行生成结果通过 JSON、Schema 与一致性校验。
2. 至少有一个用例，所有当前用例版本为 `ready`；对当前用例全集、提取规则和按事件计算的当前澄清状态重新执行 Schema、引用及一致性校验，包括明确规则是否仍有关联用例。
3. 所有当前用例版本均为 `approved`，不存在待审或退回项。
4. 不存在未处理的阻断性澄清项，包括作用于整次运行的问题。
5. 导出时重新检查当前版本、审批状态和问题状态，不能只依靠按钮是否可点击。

不满足条件时展示具体原因和关联用例/问题。门禁不会证明业务覆盖完整；这仍依赖人工审核及评测。

### REQ-EXP-02：内容与记录

- CSV：UTF-8 BOM 编码；数组以单元格内换行表示，按 CSV 规范转义逗号、引号和换行。
- Markdown：包含运行摘要、来源段落索引、用例表及必要的完整步骤分块；正确转义表格分隔符。
- 测试表包含编号、关联规则与段落、标题、前置条件、步骤、预期、优先级、分类、用例版本、通过人、通过时间。
- CSV 额外包含 `run_id`、`export_id`、Prompt 版本和输入哈希等列；Markdown 在文档头保存这些元数据。
- 对可能被电子表格解释为公式的文本安全转义；原始内容仍在数据库保留。页面和 Markdown 不执行输入或模型输出中的 HTML/脚本。
- 在同一数据库事务中固定版本清单、审批事件引用及导出内容，并记录导出者、时间、格式和内容哈希；事务成功后才提供下载。
- 导出后修改用例，不改变已生成的导出快照；历史文件在界面标识为“历史快照”，后续当前版本必须重新满足门禁。

### REQ-HIS-01：保存与查询

至少保存以下实体：

| 实体 | 主要内容 |
| --- | --- |
| Run | 运行 ID、父运行 ID、创建者、时间、模式、状态、输入摘要/全文/哈希、配置、延迟、用量、错误 |
| Paragraph | 所属运行、段落 ID、原文、类型、行号 |
| GenerationResult | 原始响应、解析结果、Schema 版本、校验结果、功能/角色/规则 |
| Clarification / Event | 问题原文、影响范围、阻断状态及后续人工处理事件 |
| TestCaseVersion | 用例 ID、版本、完整内容、来源关系、创建信息 |
| ReviewEvent | 审批与修订事件、操作者、时间、理由及状态变化 |
| Export | 固定的版本清单、审批引用、导出内容、格式、哈希、操作者与时间 |

页面刷新和应用重启后记录仍可查询。首版不提供 UI 硬删除；本地数据库和导出文件的备份由使用者管理。没有模型响应时保存错误类别与已获得信息，原始输出为空并说明原因，不能伪造原始输出或 Token 数据。

## 8. 演示 PRD 与歧义处理标准

基础业务素材：申请人提交报销单；金额大于 5,000 元需要二级审批；已审批单不可直接改金额；驳回需原因；相同发票号不得重复提交。

这些规则并不自动构成无歧义的完整 PRD。应制作一份显式补全演示所需角色、状态等细节的正常样例，并另存原始不完整样例；补充内容属于虚构样例作者的输入，不得伪装成模型从原始五条规则中推导出的事实。

| 输入情况 | 应有行为 | 禁止的推断 |
| --- | --- | --- |
| “金额大于 5,000 元需要二级审批” | 覆盖 5,000 与一个大于 5,000 的值，如 5,001；指出等于阈值不满足这条触发条件 | 推断 5,000 元以下免审；擅自规定金额精度或最小单位 |
| “大额报销需要额外审批” | 询问金额阈值及额外审批的角色/流程 | 自行写成 5,000 元或指定财务负责人 |
| 只写申请人，未写审批执行者 | 标注审批角色/权限缺失，阻断依赖该角色的用例 | 补出部门经理或财务岗位 |
| 两段分别要求“不超过 5,000 无需二级审批”与“大于等于 5,000 必须二级审批” | 同时引用两段，指出等于 5,000 时存在明确冲突并询问优先规则 | 擅自采用较严格规则或后出现的规则 |
| 已审批单不可直接改金额 | 覆盖对已审批单尝试改金额的限制 | 默认存在撤回、冲正、重新提交等替代流程 |
| 驳回需原因 | 覆盖未提供原因的驳回请求 | 补出原因最少字数、只能选枚举等规则 |
| 相同发票号不得重复提交 | 保留去重规则，询问作用范围、失败/撤回记录是否参与等执行所需信息 | 默认跨用户、跨租户或永久去重 |

仅有“大于 5,000 需要”与“大于等于 5,000 需要”两条单向触发规则时，两者不必然逻辑冲突；可以标注表述差异并询问完整适用规则，不能错误地反推等于阈值时禁止审批。

对于文本未明确的空白字符、发票大小写、负数、零金额、币种与小数位，不应把某个处理方式写成确定预期。可以形成问题；明确原文的用例可继续审核，但整次运行仍受阻断项门禁限制。

## 9. 评测方案：先冻结标准，再调 Prompt

### 9.1 数据集与标准

- 准备 20 份小型虚构 PRD，固定划分为 12 份开发集、8 份留出集，使用稳定样本 ID。
- 覆盖完整正常规则、阈值边界、角色遗漏、冲突规则、状态限制、驳回原因和发票去重等情形；场景可以组合。
- 每份标准记录：关键规则、来源段落、必须覆盖的测试条件与正确预期、应识别的歧义/冲突、禁止推断项，以及规则是否能形成可执行测试。
- 标注标准由人审核后冻结，保存数据集版本和哈希。先完成冻结，再调整 V2。
- 开发集用于调试；留出集在候选 Prompt 固定后评测，不因模型回答修改标准。
- 若标准确有错误，记录勘误并形成新数据集版本，完整重跑对比；不能把不同标准下的结果混在同一提升结论中。若看过留出结果后继续调 Prompt，该集合应注明已用于反馈，另建留出集才可再次声称独立验证。

### 9.2 对照设置

| 项目 | V1 | V2 |
| --- | --- | --- |
| 指令 | 普通生成指令，提出相同任务及字段需求 | 增加显式段落引用约束、完整 Schema、禁止补规则要求、边界检查清单 |
| 输入 | 同一份带段落 ID 的 PRD | 相同 |
| 模型与参数 | 同一模型/修订、温度、输出上限等 | 相同 |
| 后处理与判定 | 同一严格解析、Schema 和人工判定标准 | 相同 |

每份 PRD 每个版本独立运行 3 次：共 `20 × 2 × 3 = 120` 次，开发集 72 次、留出集 48 次。每个版本为 60 次。开发过程额外试跑与失败后的额外重试单列，不替换正式样本或混入正式比较。记录重复序号；服务支持 seed 时采用预先固定且对应一致的 seed，否则明确无法保证复现。

固定样例只验证程序流程，不用于声称 Prompt V2 的效果。真实模型评测使用审核前的原始输出，不把人工修订结果计作模型质量。评测顺序预先固定或交错执行，记录实际模型与时间，减少模型漂移影响。

### 9.3 指标与分母

| 指标 | 判定与统计方式 |
| --- | --- |
| 严格 JSON 合法率 | 可解析为单一 JSON 对象的运行数 / 预定执行的运行数；超时、空响应、服务错误计失败 |
| Schema 通过率 | Schema 与一致性校验均通过的运行数 / 预定执行的运行数；与 JSON 合法率分别报告 |
| 需求覆盖率 | 人工标准中被正确覆盖的关键规则数 / 标准中全部关键规则数；一条规则的必测条件均被有依据、可执行的用例覆盖才计入分子，分母不随模型输出改变 |
| 用例可执行率 | 前置完整、动作可执行、预期可判断且无阻断信息缺口的用例数 / 可评判的全部生成用例数；待澄清草稿计入分母，不计分子 |
| 无依据规则占比 | 输出中的无依据业务断言数 / 全部可评判业务断言数；对前置、步骤和预期中的规则性断言进行人工原子化标注 |
| 延迟 | 每次调用发起至响应/失败的实际耗时；另记生成加校验的总耗时；报告样本量及中位数、P95 |
| Token 与成本 | 记录服务返回的输入/输出 Token；可获取价格时保存价格版本、币种和估算方法，缺失则为 `null`，不填 0 |

补充判定口径：

- 歧义规则保留在覆盖率分母中，尚不能形成确定预期时不计为测试覆盖；正确提出澄清也不等同于可执行测试。另列“应澄清项识别率”（正确识别的标准澄清项数 / 全部标准澄清项数）及误报数量，报告总规则数和歧义规则数，解释不完整 PRD 的覆盖上限，避免鼓励编造。
- 每次运行记录各指标的原始分子与分母。覆盖率在运行失败或输出不可评判时计 0；没有关键规则的样本记为不适用，并单列样本数。数据集冻结时优先保证每份至少包含一条关键规则。
- 用例和断言指标仅在结构合格、可评判的输出上统计；失败或不可评判运行另行列出，不能把未生成的内容当作零错误。分母为零显示不适用。
- 一个用例内重复的同一业务断言计一次，不同用例中的重复断言分别计数。纯测试数据、明确标注的建议优先级不视为新增业务规则。
- 同一运行的覆盖结果去重；跨 3 次重复时按每次独立计数。开发集、留出集及 V1/V2 分开汇总，汇总率为分子总和 / 分母总和，保留逐样本差异和 3 次结果。
- 人工评分保存评判者、时间、标准版本、理由和证据位置；首版允许单人评分并注明限制。先盲化 Prompt 版本，再人工判分。

### 9.4 Badcase 分类

支持多标签：`漏边界`、`捏造规则`、`前置条件缺失`、`需求引用错误`、`预期不可判断`、`权限遗漏`；补充 `漏澄清`、`冲突未识别`、`输出格式错误`、`服务调用失败`。

每条 Badcase 关联样本 ID、运行 ID、Prompt 版本、重复序号、原始片段、标准依据及人工判断。多标签计数之和可能超过有问题的用例数。开发集的修正可进入新 Prompt 版本；保留原始结果，不覆盖旧结果。

不预写提升百分比。完成真实评测后才报告样本数、分母、标准与版本、原始结果和局限；120 次调用也不能描述为 120 份独立 PRD。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| AC-01 | 空输入、错误扩展名、编码错误、超字节/字符上限 | 显示明确错误；未发生模型调用 |
| AC-02 | 同一输入预览、生成和查看历史 | 段落 ID 与原文一致；引用可定位，输入哈希一致 |
| AC-03 | 正常固定样例 | 完整提取与用例可展示，逐条通过后可导出；界面明确未调用模型 |
| AC-04 | 固定样例未匹配 | 显示未匹配，不能伪造针对输入的生成结果 |
| AC-05 | 含糊、缺角色、阈值冲突样例 | 展示预置澄清与对应来源；相关用例不能批准，整次运行不能导出 |
| AC-06 | 非法 JSON、漏字段、非法枚举、重复 ID、悬空引用 | 分层校验失败，原始输出可查，不进入批准导出 |
| AC-07 | 当前版本有一条未审、退回，或修订后导致规则失去用例关联 | 页面和导出处理逻辑均拒绝批准导出，并显示原因 |
| AC-08 | 修改已通过用例 | 新版本待审，旧版本与旧审批保留，当前导出资格失效 |
| AC-09 | 用例被退回后修订 | 原版本不覆盖；新版本、修改理由、前后关联和新审批记录完整 |
| AC-10 | 补充业务信息后重新生成 | 新运行关联父运行，有新的输入快照与引用，审批不自动继承 |
| AC-11 | 澄清误报或调整阻断判定 | 需要依据和理由，保留处理事件，受影响用例重新审核 |
| AC-12 | 导出含中文、多行、逗号、引号和公式样式文本 | CSV / Markdown 可读，字段和版本准确，危险公式不执行 |
| AC-13 | 导出后修改、刷新或重启 | 历史导出内容不变，当前状态正确，运行与事件仍可查询 |
| AC-14 | 旧页面提交、重复提交、事务写入失败 | 不覆盖新版本，不产生重复有效事件，不留下半条修订 |
| AC-15 | 实际模型超时/调用失败 | 保存失败运行和耗时，密钥不入库，再次尝试产生关联新运行 |
| AC-16 | 评测基础设施 | 固定划分、标准和版本可核对；原始结果可重算指标，缺失数据不伪报为 0 |

AC-03/05 验证固定样例工作流，不证明实际模型具备同等能力。模型接入后需用真实评测结果单独验收质量。

## 11. 技术方案与基础工程

推荐组合为 Python + Streamlit + SQLite + Pydantic，最终依赖版本在开发开始时锁定。

职责拆分为：输入与段落处理、Prompt 模板、模型适配器、输出校验、审核与版本服务、导出服务、存储、页面、评测。审核门禁集中在服务层，避免仅依赖 UI 控件。

数据库事务保护修订、审批和导出的一致性；使用请求标识避免页面重复提交产生重复有效事件。记录应用/提交版本及 Schema 版本，以区分数据和实现变化。

基础 CI 在 PR 中执行代码静态检查、Pydantic/引用校验相关测试、审批状态与版本测试、导出门禁测试和 CSV 转义测试。CI 使用本地固定样例，不访问付费模型，不需要真实密钥。

真实模型评测单独按需执行，不进入每次提交的 CI。首版不设置未经测量的模型延迟或成本承诺；在接入时设定超时和调用预算。

## 12. 开发计划与交付物

| 阶段 | 工作 | 完成证据 |
| --- | --- | --- |
| M0：需求确认 | 确认本 PRD 和默认决策 | 用户确认后的 PRD 版本 |
| M1：固定样例闭环 | 输入、提取结果、校验、审核、版本、导出、历史 | 本地演示及相关验收结果 |
| M2：评测基线 | 20 份数据、12/8 划分、标准、指标和 Badcase 规范 | 冻结数据集、人工标注及哈希清单 |
| M3：真实模型与对照 | 接入模型，固定 V1，基于开发集形成 V2，完成重复评测 | 120 次计划调用的结果账本及真实统计；失败/未完成须单列 |
| M4：交付整理 | 修复缺陷、补齐使用说明、核对工程流程 | 可复现启动步骤、演示资料、测试与 CI 结果、评测报告 |

M1 可并行准备 M2，但 Prompt 调优必须在标准冻结后进行。M1 是本地原型闭环；完成 M1 不能表述为已完成模型能力验证或整体评测。

开发阶段将工作拆成可验收的 GitHub Issue，按 `codex/` 前缀创建分支，以提交关联 Issue，通过 PR 描述变更与验证结果。仓库和远端未配置时，先记录待完成项；没有真实 Issue、提交、PR 和 CI 证据时，不声称流程已完成。PRD 编写轮次只交付文档；用户确认后按阶段开发。

最终拟交付：源代码与启动说明、依赖配置和环境变量示例、SQLite 数据结构、固定样例、Schema、Prompt V1/V2、20 份评测输入及标准、原始评测结果与报告、基础测试/CI、CSV/Markdown 示例和演示步骤。

## 13. 待确认决策与风险

用户已整体确认以下默认值，作为开发依据：

| 决策 | 建议默认值 |
| --- | --- |
| 输入上限 | 单文件 100 KiB；正文 20,000 字符 |
| 导出范围 | 整次运行所有当前用例通过后导出；不做子集或草稿导出 |
| 澄清处理 | 未解决阻断项禁止批准导出；新增业务事实通过修订 PRD 和新运行引入 |
| 修订策略 | 任何内容修改生成新版本并重新审核；历史不覆盖 |
| 身份与部署 | 单机、单人，自报操作者标识，不提供认证 |
| 模型推进 | 固定样例先跑通；模型服务商、具体型号、预算在实际接入前确定 |
| 评测边界 | 冻结 12/8 划分，V1/V2 各重复 3 次；真实模型结果才用于效果比较 |

主要风险是：模型虽输出合法 JSON 仍可能编造或遗漏；自报操作者与本地事件不能提供真实身份认证或监管审计能力；小样本与单人判分的结论有限；实际模型耗时、费用和版本漂移会影响比较。对应措施为保留原始依据、人工复核、明确能力边界、保存评分标准与实际运行配置，而不是承诺消除这些风险。

PRD 确认前不开始实际开发；确认后按 M1 推进，实际模型与预算的选择留到 M3 接入前落实。
