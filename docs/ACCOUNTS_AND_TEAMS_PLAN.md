# 账号、个人工作与团队协作方案

- 日期：2026-10-28
- 状态：用户已确认；本地实现与验收见 ACCOUNTS_AND_TEAMS_DELIVERY.md
- 范围：登录注册、工作空间、团队入队审批、预设角色与权限、定向用例重新生成

## 1. 产品结构

登录前只提供登录和注册。登录后进入工作方式选择页：个人工作、团队协作。

工作方式不是永久绑定。每个账号拥有独立个人工作空间，也可以创建或加入多个团队；登录后可从工作空间菜单切换，后续登录优先恢复最近仍有权访问的工作空间。

团队协作首次进入时提供两个明确入口：创建团队、使用邀请码申请加入。已有团队列在下方；待审核申请单独展示，不作为可进入的团队。

个人空间和每个团队分别拥有项目、PRD、生成批次、用例、审批、导出和调用记录。团队管理员看不到成员个人空间，也不能访问其他团队。工作空间切换时清空当前审核选择、下载凭据及页面缓存，按空间保留各自需求草稿。

## 2. 账号与登录

首版使用唯一账号名、显示名称和密码注册；账号名规范化后不能重复，显示名称不能用于鉴权。提供登录、退出、已登录修改密码、会话过期提示。

删除现有手填“操作者标识”入口。生成、审核、改权限等动作均从当前登录身份取得不可变用户 ID，并保存当时显示名称快照，不能在请求里冒用其他用户。

密码使用成熟密码哈希方案保存，禁止明文或可逆保存。会话由服务端管理，登录后更新会话，退出、改密和账号停用后使相关会话失效。浏览器会话使用安全 Cookie，不把认证令牌放入 URL 或浏览器本地存储。

加入登录失败限流、生成调用额度与并发限制。首版不接第三方登录、短信及邮件找回，也不展示无法使用的“忘记密码”入口；若需要公网自助找回，作为接入邮件服务的独立交付项。

## 3. 创建团队

用户填写团队名称和可选简介。创建团队、团队空间和创建者成员关系在一个事务中完成；创建者自动成为“团队所有者（最高管理员）”，不能由前端传入其他角色。

所有者可以管理团队资料、邀请码、加入申请、成员角色和权限，并对团队所有项目的用例和澄清进行审核。管理员与所有者也使用自己的登录身份审批，不能替别人签名。

一个团队始终保留一个所有者。所有者不能直接退出或将自己降级，必须先完成所有权转移；普通管理员不能修改所有者。首版不提供永久删除团队，以归档保留历史。

## 4. 邀请码与入队审批

流程：输入邀请码 → 确认团队名称 → 提交申请 → 等待管理员审核 → 管理员选择角色并批准 / 拒绝 → 获得访问权限。

邀请码只允许发起申请，不直接获得成员身份。使用不可预测的随机码，限制有效期和使用次数，支持停用、重置以及错误尝试限流。初始默认有效期建议为 7 天；使用次数由创建邀请时设置。

申请提交时检查邀请码是否有效、是否已是成员、是否存在待处理申请，避免重复申请和重复占用次数。邀请使用次数按合法申请计数，在事务内扣减；过期只阻止新申请，不自动拒绝此前合法提交的申请。

管理员在“团队管理 → 加入申请”中查看申请人、时间和可选申请说明，选择系统角色后批准，或填写原因拒绝。批准时重新检查申请状态、审批人权限及成员是否已存在，事务化创建成员关系。并发处理同一申请，只允许一次结果生效。

待审核用户看不到团队项目、PRD、成员详情和导出，可继续使用个人空间。批准后团队出现在工作空间列表；拒绝后显示结果和原因。状态变化首版通过站内待办和刷新体现，不依赖外部邮件或聊天消息。

## 5. 系统预设角色

用户不能自行填写角色名称或声明自己是管理员。管理员为成员从以下预设角色选择：

| 能力 | 所有者 | 管理员 | 用例编辑者 | 审核者 | 观察者 |
| --- | --- | --- | --- | --- | --- |
| 查看团队项目、需求与用例 | 是 | 是 | 是 | 是 | 是 |
| 创建项目、提交 PRD、生成用例 | 是 | 是 | 是 | 否 | 否 |
| 人工修改用例 | 是 | 是 | 是 | 否 | 否 |
| 通过 / 退回用例、处理澄清 | 是 | 是 | 否 | 是 | 否 |
| 触发退回用例的定向重新生成 | 是 | 是 | 是 | 是 | 否 |
| 生成或下载批准导出文件 | 是 | 是 | 否 | 是 | 否 |
| 管理邀请、审批加入申请 | 是 | 是 | 否 | 否 | 否 |
| 分配普通成员角色与权限 | 是 | 是，受权限上限约束 | 否 | 否 | 否 |
| 任命 / 撤销管理员、转移所有权 | 是 | 否 | 否 | 否 | 否 |

角色提供默认权限模板。成员详情提供有限权限开关，覆盖“生成、编辑、审核、导出”等业务能力，不开放任意权限字符串或自定义角色。管理员不能授予自己没有的能力，也不能通过权限开关获得所有者专属操作；只有所有者可以授予管理员身份。

首版团队成员按权限访问团队内全部项目，不叠加项目级成员名单，避免首轮同时引入两套授权规则。后续若需隔离团队内敏感项目，再增加项目级授权。

首版允许有审核权限的人审核自己参与生成的用例，不强制双人审批。所有者的“最高权限”表示可以操作团队内所有审批对象，不能跳过结构完整性、未解决阻断问题、版本冲突或人工审批记录。

成员被降权、停用或移除后，后续请求立即重新查验权限；已有历史事件保留。后台任务在提交与写回时检查归属、身份和版本，不能因为执行期间权限变化而覆盖较新的内容；已经返回的团队生成记录仍归团队保存。

## 6. 个人工作流程

个人工作不展示团队成员、角色、邀请和入队审批，也不要求用户分配权限。用户只管理自己的项目。

主流程：输入 PRD → AI 提取功能、角色、规则、问题与用例 → 用户逐条审核 → 退回用例定向重新生成 → 再次审核 → 全部通过后导出。

角色提取是需求文档中的业务角色，与系统协作角色完全分开。例如 PRD 的“申请人”不能赋予系统的团队管理员权限。

退回规则：

1. 用户填写必填的退回原因，点击退回；先保存退回事件，再创建定向生成任务。
2. 任务输入包括原 PRD、相关来源、当前这条用例、退回原因和输出约束。退回意见是审查反馈，不能充当未写入 PRD 的新业务事实。
3. 模型只返回目标用例的新内容，保留用例编号并创建新版本，状态为待审核。
4. 其他用例内容与版本不变，已有批准记录继续有效；旧的退回版本、原因、输入及原始响应保留。
5. 页面显示“已退回，正在重新生成”，用户可以继续审核下一条。生成结束后在待办中提示，点击回到新版本。
6. 失败时显示可理解原因并提供重试；保持未批准状态，不用旧版本悄悄替代，也不无限自动重试。格式修复仍限制为一次自动尝试，调用记录分开保存。
7. 如果用户已修改目标用例，迟到的模型响应不覆盖新版本，保留为冲突结果并提示处理。重复点击不会创建多个相同任务。

如果意见涉及新增或修改业务规则，先更新 PRD 并创建关联新批次，不能把它混入单条修订；新批次重新审核，不沿用旧需求的批准。

## 7. 团队复用现有模块

保留项目概览、PRD 输入、需求分析、用例库、澄清、审核、生成历史与导出模块，增加工作空间入口、成员管理和加入申请。

个人与团队共用一个生成、版本、审批和导出引擎。团队同样支持定向重新生成，区别在于执行者需具备相应权限，而不是维护另一套审核逻辑。审核者退回所触发的定向生成，不等同于获准任意创建 PRD 生成任务。

同一版本被多人同时审核或修改时，提交时校验版本；先提交者成功，后提交者获得“内容已更新，请刷新核对”的反馈，不能覆盖他人审批。重复相同提交使用幂等键去重。

导出条件统一为：当前所有用例均通过、无未解决阻断问题、导出者具备权限。任何用例退回、修改或正在重新生成，都不能导出该批次当前批准版本。历史文件可在仍具备权限时下载，但明确标为历史快照。

延续现有覆盖提示：规则尚无关联用例时明确标注缺口，批准现有用例不代表完整覆盖；CSV / Markdown 保留该说明，不以丢弃已生成用例解决质量问题。

## 8. 数据归属与技术改造

现状只有 `project_id` 隔离和自报操作者，不能直接承载登录后的多人协作。

新增核心对象：User、Session、Workspace、Team、Membership、Invite、JoinRequest、PermissionOverride、GenerationJob。现有 Project 绑定 Workspace；Run、CaseVersion、Clarification、ApprovalEvent、Export 通过项目关联空间。事件增加真实操作者 ID，保留当时名称及旧历史标签。

项目名称唯一约束改为“同一工作空间内唯一”。个人和不同团队可以存在同名项目。项目不能通过更换前端参数迁移到其他空间。

保留当前 Streamlit 页面风格与业务模块，增加后端认证、权限及任务服务。建议后端 API 采用 FastAPI；登录会话、资源授权和下载检查放在服务端，通过同源访问接入界面。长时间模型调用进入后台任务，避免阻塞审核页面。

本地阶段可继续使用 SQLite 完成迁移和受控并发验证；公开多人部署前使用 PostgreSQL 与共享任务存储，验证会话、数据隔离和并发。首版不同时引入第三方登录、复杂组织层级、项目级 ACL 或自定义角色编辑器。

每次读取、审批、模型提交、后台写回、导出和文件下载都验证身份、有效成员关系、工作空间及操作权限。前端隐藏按钮只用于体验，不能代替服务端授权。请求幂等和缓存同样包含用户与空间上下文，不能在切换账号或空间后返回上一个人的结果。

模型配置继续由维护者在后台管理，不回到用户页面；调用记录归属到用户和空间，支持按空间限制额度与并发。

## 9. 现有数据迁移

升级前备份数据库并执行版本化迁移，保留 PRD、原始响应、用例版本、审批事件和导出文件。

现有无账号归属的数据先留在隔离的迁移区，不自动分配给第一个注册人，也不允许公共注册账号抢占历史数据。由本机维护者通过受控迁移操作明确归入指定个人或团队空间。

旧操作者标签原样保留，标识为历史自报身份，不回填为某个新账户的真实审批。原导出文件不改写，迁移后仍受空间与下载权限控制。

## 10. 实施顺序与验收

1. 账号、登录会话和个人空间隔离；移除手填操作者。
2. 单条退回 → 后台定向生成 → 新版本复审；验证未改用例的批准记录保留。
3. 团队创建、邀请码、申请审批、预设角色和权限开关。
4. 将现有全部项目、审核和导出功能接入空间及权限检查。
5. 迁移已有数据，并完成端到端、多账号、并发和越权回归。

重点验收：未登录不得读取数据；账号 A 无法访问账号 B；团队之间及团队与个人空间互不可见；邀请码不能直接入队；待审核申请无资源权限；管理员不能提升自己或修改所有者；降权后旧页面和旧下载请求不能继续执行；并发审批不覆盖；模型只修改被退回用例；失败与迟到结果不恢复批准；未全部通过不能导出。

本文件保留已确认的设计范围。实现状态和运行／迁移说明见 [交付说明](ACCOUNTS_AND_TEAMS_DELIVERY.md)。
