# TraceCase 测试工程师 Agent 产品方案

日期：2026-11-03。设计基于代码 9bd5ad3；Agent 实现已落地到 codex/testing-agent。本文保留产品目标与后续阶段，实际交付、验证证据和边界以 AGENT_IMPLEMENTATION.md 为准，不将拟议调研或后续集群部署视作已完成。

本文从测试工程师需要完成的工作推导产品行为。需求来自现有用户反馈、现有功能摩擦和典型测试工作方法；尚未开展目标团队访谈，不能将假设表述成已验证用户结论。前一份 AGENT_AND_PRODUCTION_ROADMAP.md 继续作为工程基础方案，本文明确先做哪些用户价值、交互和验收。

## 1. 下一版定位与目标用户

定位：帮助测试工程师完成需求评审、测试设计和需求变更维护的项目级 Agent。

第一批用户：需要自行阅读需求、编写和维护功能/API测试用例的小型研发团队测试人员，以及独立承担测试工作的个人用户。团队测试负责人关注覆盖、协作进度和交付；产品或业务负责人作为澄清答复与需求确认的协作者。

用户交给系统的是一项具体任务：为某个需求版本完成测试准备，或在需求变化后更新已有测试。Agent 的自主性体现在选择资料、定位缺口、组织生成与局部修订，并能等待答复后继续。

首版交付目标：在指定范围内，得到有依据、可执行、经人工评审的用例基线，以及清楚的未解决问题。测试执行、缺陷确认和发布批准单独管理。

## 2. 从日常任务出发的需求假设

| 用户要完成的工作 | 我希望平台提供的体验 | Agent 主动做什么 | 验证价值 |
| --- | --- | --- | --- |
| 收到一份新需求，准备参加评审 | 先看重点、风险和待确认问题 | 读章节与表格、整理角色/状态/规则、定位冲突和测试阻塞 | 阅读整理时间、有效问题比例、关键未知遗漏 |
| 为明确需求设计测试 | 看得出测了什么、为什么测、还缺什么 | 先建立测试条件，再生成、复用、去重与检查 | 关键条件覆盖、可执行率、无依据断言 |
| 产品更新需求 | 直接看哪些用例要改、为什么要改 | 比较版本、沿依赖分析影响、提出新增/修改/停用建议 | 维护时间、真实影响召回、无必要修改 |
| 审核和退回用例 | 看修改差异，避免一遍遍读整套用例 | 分类反馈、修订目标、提示同类问题 | 审核耗时、修订接受率、重复错误 |
| 准备交付或回归 | 清楚当前范围的完成度、缺口和下一步 | 汇总批准基线、阻塞、回归建议与依据 | 交付准备时间、追溯完整、建议采纳原因 |

优先研究两个反复发生的任务：新需求测试设计、需求变更维护。真实使用中还可能需要探索式测试、环境与数据准备、自动化脚本和执行结果分析；这些应依次接入，避免同时扩张全部测试生命周期。

## 3. 一天的目标体验

### 新需求进入

用户进入项目，看见当前任务、待答问题和待评审内容。点击“新建测试任务”，粘贴或上传 PRD 即可开始；可选补充“重点看权限与边界”“只做本次审批改动”“希望先得到冒烟场景”。

没有填写额外选项时，系统按全量明确需求先做分析和设计。目标含糊但有安全默认值时展示默认范围并允许修改；多个版本或互相冲突的范围无法消解时只询问关键问题。基本解析和明确部分生成不必等待用户逐阶段点确认。

任务页尽早展示：已识别模块、关键规则与来源、可开始评审的用例、待答问题、尚未处理范围。用户能一边评审明确部分，一边等待其他模块。

### 需求评审与答复

问题卡展示“缺什么、来自哪里、影响什么、由谁确认”。用户可以回答、标记不知道、指定协作者、依据原文指出误报。系统没有答案时保留问题，并继续不受影响的工作。

答复包含新业务事实时形成需求补充提案；具有需求确认权限的人确认后，保存新版本并只推进受影响部分。不能让评论或退回理由自动成为有效业务规则。

### 用例评审

用户以覆盖树和风险顺序查看用例。右侧可展开原文依据；修改后首先看差异和修改原因。通过操作可快捷完成；退回选择原因并填写必要说明。

纯用例质量问题可自动修订为新候选版本；业务规则变化等待需求确认；重复项提出合并/停用建议。用户继续评审其他用例，不必等待每次模型返回。

### 次日需求变化

重新上传时，系统识别同项目的需求更新并展示差异候选。用户确认要比较的旧版后，Agent 定位受影响用例；原有批准不会因生成了新任务而无条件丢失，也不会因旧内容曾获批准而自动适用于新需求。

### 交付

指定任务范围全部满足评审条件后，生成批准用例基线与交付说明。界面明确标注适用需求版本、范围、排除项、已知问题、批准状态和执行状态。执行尚未开展时显示“未执行”。

## 4. 用户任务与 Agent 能力

产品初期只有一个面向用户的项目测试 Agent。内部可分分析、规划、生成、复核节点，但用户不需要切换多个角色或管理 Agent 数量。

| 能力 | 输入与上下文 | 行动选择 | 用户可见成果 |
| --- | --- | --- | --- |
| 需求评审 | 本次需求版本、已确认项目规则 | 定位跨章节定义、冲突、缺失执行条件 | 需求地图、风险卡、问题卡 |
| 测试设计 | 明确规则、目标范围、既有批准用例 | 选等价类/边界/决策表/状态转换等方法，补缺口 | 覆盖计划、候选用例、方法依据 |
| 用例修订 | 目标版本、反馈、需求依据 | 修步骤/预期，或转需求确认，或提合并建议 | 差异、解释、未解决反馈 |
| 变更影响 | 两版需求、用例依赖 | 直接与间接影响定位、局部生成 | 影响列表、受影响待复核标记 |
| 回归准备 | 变更、风险、有效用例、已知依赖 | 建议必测/扩展范围、标明未知影响 | 可确认的回归集合与原因 |

测试方法属于系统可应用的专业知识；阈值、权限、SLA、金额精度、错误码属于业务事实，必须来自需求或已确认补充。探索建议可以超出已描述路径，但须明确为“建议验证的风险/待确认预期”，不能被混写为确定业务规则。

### 用例的质量要求

- 一条用例具有明确测试意图、角色、初始状态、测试数据/数据准备、操作和可观察预期。
- 有必要时补充清理/恢复条件；不能每条都机械填写无关字段。
- 同一操作的等价数据可参数化，避免把每个值展开成重复长用例。
- 对组合条件先判断可达性和业务约束，避免生成不可能的状态组合。
- 边界值按已确认的单位和精度计算；未知时提出问题。
- 关键权限、状态转换、重复操作和异常条件按需求适用性检查。
- 相同项目的有效批准用例可被推荐复用；复用前检查版本和依赖。跨项目复用默认需要显式授权。
- 去重和合并先给建议与影响，不静默删除历史用例。

## 5. 工作界面

### 项目工作台

项目内默认入口从技术性的运行列表转为任务工作台：

1. 主操作：“新建测试任务”“分析需求变更”。
2. 我的待办：待答问题、待评审、待确认变更、失败待恢复。
3. 当前任务：目标、需求版本、负责人、真实阶段、最新产物、继续按钮。
4. 项目概况：当前需求基线、批准用例范围、未解决风险；生成数量只作为工作量。

个人与团队复用同一任务流程；团队增加负责人、需求确认人和评审人。身份来自真实成员，不再手填角色。邀请、成员和权限仍由已有团队管理承载。

### 任务详情

页面顶部固定展示任务目标、项目、需求版本和范围。主体提供“需求与问题 / 测试覆盖 / 用例评审 / 交付”四个视图；进度侧栏或抽屉展示 Agent 当前动作、已完成工作和下一步。

聊天/自然语言输入作为上下文补充和批量意图入口。问题答复、评审、版本对比与导出使用结构化卡片和按钮；用户不必在长聊天记录里寻找真实数据。

关键动作卡示例：

- “审批人未定义，影响权限用例。查看依据并回答。”
- “金额边界缺少等值场景。正在补充相关草稿。”
- “修订涉及新的审批阈值。请确认需求变化。”
- “模型建议已落后于人工修改。查看冲突，选择是否采纳。”

模型名称、参数、内部 Prompt 版本、JSON、调用记录默认置于维护/诊断区。用户主要看目标、依据、结果和待决定事项。

### 覆盖视图

使用“模块 → 已确认规则 → 测试条件 → 用例”的树或矩阵。每项标记未设计、草稿、待澄清、待评审、评审通过、受影响待复核或本次范围外。点击缺口即可查看依据并让 Agent 提出补充。

覆盖率的分母与版本必须可查看。首版可以展示“已识别规则的关联覆盖”；未经独立确认不能把这个数称为完整需求覆盖，更不能据此宣称产品质量达标。

## 6. 减少无效打断的自主性与确认

| 行为 | 自动执行策略 |
| --- | --- |
| 读取当前授权范围资料、解析、提取、检查、创建草稿 | 用户提交任务后直接推进 |
| 发现缺口后检索相关项目规则、补生成、有限修复 | 在任务范围和预算内执行，展示进度 |
| 对退回的纯用例问题修订 | 创建新候选版本，不直接批准 |
| 对类似错误扩大修订范围 | 先提出关联清单，由用户选择范围 |
| 将答案作为新的业务事实 | 授权人员确认需求补充 |
| 接受范围排除、沿用批准、合并/停用用例 | 展示影响并记录人工决定 |
| 正式评审通过、批准导出、写入外部平台 | 按真实权限和业务门禁执行 |

Agent 在每步说明简短行动理由和依据。任务没有有效进展、遇到冲突或耗尽预算时给明确恢复入口；不能无限反思，也不能反复要求用户点击“继续”完成本来已授权的工作。

## 7. 反馈路由

当前退回后会立即排队修订。下一版建议在退回时先分类：

| 反馈原因 | 系统动作 |
| --- | --- |
| 步骤不清/预期不可判断 | 定向改写，缺依据则提出澄清 |
| 漏边界/权限/状态场景 | 校验原文是否明确，提出补充或拆分用例 |
| 无依据业务规则 | 定位不支持的断言，移除或转待澄清 |
| 与其他用例重复 | 提出合并、参数化或停用建议 |
| 需求已经变化 | 转需求变更确认，不立即盲重生成 |
| 仅表达偏好 | 修改表达；可选择保存项目写作偏好 |

同类错误可能影响其他用例时，系统提示范围和理由；默认只改用户指定对象。偏好不能覆盖事实，业务新规则不能只存成提示词。

## 8. 状态语义与完成标准

任务进度、用例设计评审与测试执行分开建模。

| 类型 | 例子 | 解释 |
| --- | --- | --- |
| Agent 任务 | 处理中、等待答复、等待评审、部分完成、完成、失败、取消 | 测试准备任务的推进情况 |
| 用例设计 | 草稿、待澄清、待评审、评审通过、退回、受影响待复核、停用 | 用例内容是否适合使用 |
| 测试执行 | 未执行、执行中、通过、失败、阻塞、跳过 | 在具体环境/构建上的实际结果 |

首版没有执行能力时，仅记录未执行，不伪造执行结果。评审通过是设计决策，不能在报告中变成测试已通过。

测试准备任务完成须满足：目标范围与需求版本确定、当前应交付用例完成评审、阻断问题已解决或通过明确范围调整处置、覆盖缺口与排除项可见、基线可追溯。后续需求更新时已完成任务仍保留历史，新建变更任务。

范围调整不能静默移除被退回内容；必须说明排除原因、确认人和影响，并保持项目未解决项可见。

## 9. 新增数据与工程支撑

用户需要的连续工作体验依赖以下增量，而非仅增加聊天 UI：

- 测试任务：目标、范围、输入版本、负责人、确认人、阶段、预算、下一步。
- 文档/需求的稳定身份、版本和来源锚点；现有 P001 编号可继续展示，但不作为跨版稳定身份。
- 测试条件与覆盖计划、规则/用例多对多依赖、风险与范围排除。
- 澄清答复及确认事件；变更提案及影响关系。
- 用例稳定身份及修订、差异、审批事件和批准基线。
- 工作流阶段、尝试、工具调用、产物与可恢复检查点。

保留账号/空间授权、Provider 抽象、版本冲突检查、历史快照与导出门禁。逐步将本地线程池升级为独立 Worker 和持久任务调度，迁移 PostgreSQL 时专门验证审批事务。关闭页面后任务仍可继续；服务重启恢复未完成阶段；撤权后不得越权提交。

Agent 的上下文由服务端绑定项目与版本。工具仅允许授权资料检索、覆盖检查、草稿生成和修改提案等行为。模型无权批准、修改成员权限或任意读取其他项目。每次任务限制调用次数、时间与成本，额度信息由维护者管理，用户只需看到任务能否继续和恢复方式。

## 10. 分阶段交付

### 里程碑 A：一个新需求测试准备任务能完整走通

**范围**：任务入口与工作台、目标/范围、版本化依据、分析与覆盖、分批草稿、问题答复确认后续跑、反馈分类与定向修订、差异评审、批准基线。可恢复任务底座随本里程碑建设。

用户仍可只输入 PRD 直接开始；额外目标可选。每一步既有明确状态，也有用户可检查的产物。

**核心验收剧本**：

1. PRD 含明确金额规则但缺审批角色：明确内容产生草稿；角色相关用例待澄清，不自动补角色。
2. 用户回答并由有权人员确认：只处理受影响内容，其他用例不重复生成。
3. 退回“预期不清”：给出带依据的新版本差异，再人工评审。
4. 退回“产品已改规则”：等待需求确认，无效修订调用不发生。
5. 人工修改期间模型返回：旧建议成为冲突提案，不覆盖当前版本。
6. 关闭页面或中断 Worker 后回来：进度和已完成产物保留，可以恢复。
7. 全部用例设计评审通过：导出批准基线；执行状态仍是未执行。

### 里程碑 B：第二版需求到来时只维护受影响内容

**范围**：需求版本对比、稳定需求与用例身份、影响分析、修改/新增/停用建议、批准复用策略、差异复审；复用当前项目已批准用例。

**验收**：将“大于 5,000”改为“大于等于 5,000”，定位等值边界与相关审批路径；无法确定的间接影响待复核；旧基线可回看，未受影响内容不被无理由改写。

### 里程碑 C：进入现有测试协作流程

**范围**：用户既有用例 CSV 导入与字段映射、共享前置条件/步骤与数据准备、按风险和变更建议回归集合、负责人/截止时间/站内待办、面向一个实际使用工具的导出适配。

外部平台先读/导入，写入前展示具体差异并按权限确认。根据试点选择一个连接器，不预先建设所有平台。未经授权不自动向其他人发送消息。

### 后续：结合真实执行证据

有实际需求后，支持用户记录测试结果或导入 CI/API/UI 自动化报告，并关联用例版本、构建、环境与执行时间。Agent 可整理失败和缺陷建议，但根因与缺陷状态仍需证据确认。自动操作被测系统另建隔离、凭据、清理和人工控制边界，单独立项。

## 11. 真实需求验证与价值评测

建议首轮邀请 5–8 名目标测试人员，并邀请产品/测试负责人参与澄清与评审环节；这是拟议调研规模。覆盖个人、小团队评审和频繁需求变更场景，使用经授权脱敏的实际材料。

让用户做具体任务并观察行为，而不是只询问“是否喜欢 Agent”：

1. 准备一份新需求的测试内容。
2. 找出平台缺失或误解的关键规则。
3. 回答一个会影响多条用例的问题。
4. 修订一条错误用例。
5. 处理一次需求变化并交付新版测试基线。

记录现有方法与新流程的阅读、补充、审核、返工和交付时间，分任务复杂度比较；尽量平衡任务顺序，降低学习效应。结果保留原文、产物、人工判定和版本。不要把同一材料多次运行当成独立需求样本。

核心价值指标：完成一个达标测试准备任务的人工主动操作时间。质量门槛包括人工标准覆盖、关键漏测、可执行率、无依据断言率、有效澄清比例；成本与任务恢复情况单独报告。用户点击通过只能作为操作记录，不能直接充当质量 gold。

需求变更重点看真实受影响用例召回率、无必要修改率、维护耗时。初期不知道无影响的对象不能擅自计入批准复用成功。

第一轮先建立基线，按观察结果设目标，不预设“提高 30%”等宣传数值。若 Agent 产出的内容让人花更多时间辨错，即使生成速度快，也应视为需要改进。

## 12. 首批工程 Issue 建议

1. 定义测试任务对象、状态、输入版本与完成标准。
2. 项目任务工作台与待办，隐藏技术运行作为默认主入口。
3. 持久阶段任务、产物、恢复与真实进度。
4. 版本化证据与原子规则，需求/测试条件/用例覆盖关系。
5. 分模块生成、质量检查和缺口补充；保留部分成功。
6. 澄清答案与需求补充确认、局部续跑。
7. 退回原因路由、修订差异与同类问题范围建议。
8. 批准基线与评审/执行状态文案分离。
9. 试点任务与人工评分表，实际模型和人工耗时对照。
10. 需求变更影响与批准复用，作为第二个完整切片。
