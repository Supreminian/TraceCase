# 项目管理与用例归属方案

版本：P1.0 · 2026-10-27 · 用户已确认，实现已完成

本方案已获用户确认。项目归属、页面与迁移已实现，实际测试和迁移记录见 VERIFICATION.md。

## 1. 目标与核心关系

将当前全局运行列表改为按项目组织。每个项目有自己的 PRD 输入、生成批次、测试用例、审核记录、修订迭代和导出文件。

```text
项目
  ├─ 生成批次 A（输入 PRD 快照）
  │    ├─ 用例与版本
  │    ├─ 审核/澄清事件
  │    └─ 批准导出快照
  └─ 修订批次 B（关联 A，同属一个项目）
       ├─ 修订后的用例
       └─ 新一轮审核与导出
```

一个生成批次只属于一个项目；用例通过批次归属项目。项目内可以有多次独立生成和多轮修订，不能把所有批次的用例混成一份审批结果。

现有用例编号（如 TC001）保留为可读编号，真实定位使用项目 ID、运行 ID、用例编号和版本。不同批次编号相同不表示同一个逻辑用例；首版不自动合并或去重。

## 2. 首版功能

### 项目列表与维护

- 新建项目：项目名称必填，建议限制 1–80 字符；简介选填，最多 500 字符。
- 名称去除首尾空白，在现有项目范围内不允许重名；稳定项目 ID 不随改名变化。
- 编辑名称与简介，保留操作者、时间及修改记录。
- 归档/恢复项目。归档后可查看历史、下载已有快照，不能新生成、审核、修订或生成新的批准导出。
- 存在生成中的批次时先等待完成或明确记录中断，再归档，避免半途改变任务资格。
- 首版不提供硬删除、跨项目搬迁或复制用例，以免破坏来源与审批关系。

### 项目工作区

顶部持续显示当前项目名称，侧栏提供项目切换与“项目列表”入口。未选择项目时先进入项目列表，不能在无项目上下文中生成用例。

工作区包含：

| 入口 | 内容 |
| --- | --- |
| 项目概览 | 项目简介、最近批次、生成中/失败数量、待审核与退回情况，以及继续处理入口 |
| 生成用例 | 在当前项目中输入 PRD、选择模型并生成；每次保存完整输入快照 |
| 项目用例 | 按批次查看当前用例版本，按待审核/通过/退回/优先级/分类筛选，点击进入审核 |
| 审核与修订 | 沿用快速通过、退回、自动切换、审核结果与模型/人工迭代流程 |
| 批次历史 | 本项目的全部运行、父子迭代关系、原始结果、失败原因和事件 |
| 导出记录 | 本项目的批准快照，包含准确批次与版本信息 |

项目用例默认展示最近一个校验通过批次，明确显示其批次标识；同时提示是否有更新的失败/待处理批次，避免把旧结果误认成最新结果。所有批次均可切换查看，早期批准快照不自动成为新需求的批准版本。

## 3. 审核与迭代规则

- 新建生成时，服务端固定项目 ID，保存至运行记录；客户端切换项目不能改写已提交任务的归属。
- 模型修订、补充 PRD 后重新生成，必须继承来源批次的项目。拒绝跨项目父运行引用。
- 人工修订在所属项目的原运行生成新版本；只重审改动项。
- 模型修订在同项目创建关联新运行；已通过内容锁定，新运行仍全部重新审核，不继承批准。
- “全部通过自动进入导出”和“有退回进入审核结果”仅针对一个批次，不把不同批次的批准拼接。
- 项目概览中的待审/退回数量按当前用例版本统计，保留批次维度。这是工作量提示，不代表项目整体已经通过或失败。
- 默认不支持一次导出项目中多个批次的合并用例；先保留当前整批批准门禁。

## 4. 项目切换与防串数据

本功能的关键不仅是页面筛选，还包括服务端归属检查：

1. 读取批次、用例、澄清、事件和导出文件时，均验证其所属项目与请求项目一致。
2. 审批、修订、模型迭代和导出提交均携带项目 ID，并校验运行归属、当前状态与版本；不能只检查侧栏当前选择。
3. 请求幂等指纹包含项目 ID，避免同一请求键在不同项目错误复用。
4. 项目切换时，清理旧项目的审核定位、完成导航和下载准备状态；新项目不能显示上一项目的下载按钮或审批表单。
5. PRD 草稿、父批次选择和最近查看的批次按项目分别保存。切回原项目可以继续草稿，不能带入其他项目。
6. 模型只接收本次运行所需的 PRD 和本项目来源反馈，不默认将项目全部历史输入模型。
7. 已发出的模型请求即使稍后返回，也只能写入提交时绑定的项目；不能按届时页面上的项目选择重新归属。

这里的项目隔离用于保证本地原型的数据归属。当前仍为单机、自报操作者，不宣称项目成员权限或租户安全已经完成；未来认证授权应在这些归属检查之上增加。

## 5. 导出与改名

- 新导出的 CSV/Markdown 包含项目 ID、导出时的项目名称、运行 ID 和原有审批/版本元数据。
- 文件名采用安全项目标识及运行/导出 ID，不直接拼接未经处理的项目名称。
- 项目改名只影响当前展示；历史导出保留当时的名称与文件内容，不重新生成或改写。
- 下载已有历史快照同样验证项目归属。

## 6. 现有数据迁移

建议自动创建一个“历史项目”，将现有全部运行及其父子迭代关系绑定到该项目，之后可改名。系统不凭 PRD 内容猜测原记录实际属于哪个项目。

迁移要求：

- 先通过 SQLite 一致性备份方式保存迁移前数据库，兼顾 WAL；不能在运行中简单复制一个数据库主文件冒充完整备份。
- 使用数据库版本迁移，在事务中创建项目并补全运行归属，验证父子关系和外键，成功后再提交新版本号。
- 移除当前每次启动固定写入数据库版本 1 的方式，改为只执行尚未完成的迁移；发现更高的不支持版本时拒绝静默降级。
- 保留原运行 ID、用例版本、原始输出、事件、审批状态与文件哈希，不重写既有批准快照。
- 旧快照文件原先没有项目字段，其归属在界面和数据库关联中显示；不向旧文件补写内容。
- 迁移可重复检查但不能重复创建“历史项目”；失败回滚，保留可恢复的备份。

## 7. 数据与服务改动范围

新增 projects，保存稳定 ID、名称、简介、状态、创建/修改时间及操作者；新增项目维护事件，记录改名、归档和恢复。

runs 增加非空 project_id 外键，并为项目和时间建立查询索引。用例、审批与导出继续通过不可变 run_id 归属项目，避免在多张表中重复维护容易不一致的项目字段。

生成、查询、审核、澄清、修订与下载服务显式接收项目上下文，在服务层验证。UI 不再用全局 list_runs 取全部原文/输出后自行筛选；项目/批次列表分页或限制展示数量，按需读取详情。

本期继续使用 Streamlit + SQLite，不因增加项目管理就引入微服务、Redis、独立认证平台或多租户。上线方案另见 PRODUCTION.md。

## 8. 验收场景

| 编号 | 验收要求 |
| --- | --- |
| PJ-01 | 新建、改名、归档与恢复成功，名称校验明确，项目 ID 稳定 |
| PJ-02 | A/B 项目分别生成，彼此的用例、原文、运行、审批与导出不串入当前工作区 |
| PJ-03 | 修改请求中的项目/运行/导出 ID，服务端拒绝跨项目读写与下载 |
| PJ-04 | 项目切换不提交旧审批、不混入旧 PRD 草稿，也不显示旧下载内容 |
| PJ-05 | 人工修订与模型迭代保持同项目归属，跨项目父运行引用被拒绝 |
| PJ-06 | 单批次审批与导出门禁保持生效，项目级统计不能绕过当前批次审核 |
| PJ-07 | 归档项目只允许读取与下载已有快照；新生成、审批与修订被拒绝，恢复后可继续 |
| PJ-08 | 历史迁移不丢记录、不破坏父子关系、不改变旧文件内容/哈希；重复启动不重复迁移 |
| PJ-09 | 项目改名后，新导出使用新名称，旧快照保持导出时名称及原字节内容 |
| PJ-10 | 模型迟到结果、旧页面操作及重复请求不会写入错误项目 |

## 9. 实施顺序与默认决策

1. 项目模型、版本迁移、历史项目与归属校验。
2. 项目列表/切换、项目用例与批次查询。
3. 审核、迭代、导出与草稿的项目绑定。
4. 迁移/隔离/页面流程测试，核对现有审核回归。

建议整体确认的默认方案：

- 现有数据全部归入“历史项目”，不自动分类，不丢记录。
- 项目下面保留多个批次，不自动合并重复编号的用例；首版按单批次审核与导出。
- 支持归档/恢复，不做硬删除与跨项目搬迁。
- 首版继续单机使用；项目归属与多人权限分开实施。
