## 1. 产品方向与现状

建议将产品定位为“持续维护需求与测试之间关系的协作工作台”：上传需求、提取规则、发现不确定性、生成测试、人工复核、变更影响分析、形成批准基线。初期重点服务中小研发团队的功能/API测试设计。测试文档生成与软件测试执行是两种能力，应分别验收。

第一阶段应选择少量有代表性的试点团队，明确每周文档数量、文档长度、现有测试管理工具、审核耗时和数据敏感级别。首批验收可聚焦 Markdown、表格、跨章节约束和需求更新；DOCX、PDF/OCR、自动执行可分阶段增加。

## 2. Agent 的职责边界

采用“确定性业务状态机 + 有边界的模型决策”。普通工作流由代码决定下一步；Agent 在允许的工具集合中，根据证据决定检索哪些资料、补哪些测试、提出什么澄清。不是所有节点都需要一个独立 Agent，也不需要先建立多 Agent 自由讨论系统。

推荐三种任务角色，可以是同一 Worker 内的三个节点，复用模型适配器：

1. 需求分析：提取原子规则、角色、状态、约束和冲突，为每项结论附原文依据。
2. 测试规划与生成：建立覆盖计划，按模块生成，针对缺口调用补生成工具。
3. 证据复核与修订：检查预期是否受依据支持，处理人工退回和需求变更，产出差异提案。

结构校验、授权、版本比较、预算、审批、批准导出由代码执行。审查模型可以指出问题，但不能成为自动批准者。只有当拆成多个 Agent 的收益在评测中超过成本与延迟，才进一步拆分。

可提供给 Agent 的工具：

| 工具 | 范围 | 结果 |
| --- | --- | --- |
| read_document_revision | 当前授权项目的指定版本 | 原文片段与证据锚点 |
| search_project_context | 已授权、明确版本的项目资料 | 片段、来源、版本、状态 |
| inspect_coverage | 固定需求集合 | 缺失的测试条件与关联证据 |
| generate_case_batch | 计划中的一组需求 | 待校验候选用例 |
| propose_clarification | 指定需求与证据 | 待人工回答的问题 |
| propose_case_revision | 指定用例版本与反馈 | 修改提案、差异、未解决问题 |
| validate_artifact | 结构化候选产物 | 机器校验报告 |

tenant/workspace/project/actor 由服务端授权上下文注入；模型不能通过参数更换身份或租户。初期不暴露任意 SQL、Shell、文件系统、任意 URL 访问、成员权限修改、审批通过和批准导出工具。外部连接器后续单独授权，默认只读；写入测试管理平台前展示可审核的具体差异。

每个工作流必须具有最大步骤数、模型调用数、工具调用数、Token、费用和墙钟时间限制。每个失败批次的修复上限可先设为 2 次作为实验配置；发现同样错误再次出现、无质量进展或达到预算时转人工并保留已有产物。该上限是建议值，不是已实现参数。

## 3. 目标生成流程

1. 接收并保存原始文档，校验格式、编码、大小和权限。
2. 解析标题、列表、表格和引用，建立版本化证据块。先保留 Markdown 的完善支持，再增加其他格式；OCR 结果需要标注解析不确定性。
3. 全局抽取角色、术语、规则和依赖；每条规则具有稳定身份、版本及来源。
4. 建立覆盖计划：正常流程、边界、权限、状态转换、重复提交、外部依赖异常等。适用性必须来自需求；“建议补充性能目标”不是已经确定的性能需求。
5. 按业务模块或用例批次生成，带入相关全局约束。批次大小根据 Token 估算和输出预算确定，不机械按字符截断。
6. 每批独立执行结构和引用校验、语义证据复核，保存可审核的完整用例。
7. 汇总跨模块冲突、覆盖缺口和问题；仅对缺口或失败批次有限补生成。
8. 人工审核；遇需求空缺时进入澄清。退回则定向修订，修改形成新版本。
9. 明确范围内当前用例全部批准且没有阻断问题，才建立批准基线并导出。

明确部分尽早呈现为可审核草稿；有问题的批次显示原因和下一步。不能把截断 JSON 硬补括号后当作完整结果，也不能让局部缺信息导致整份明确需求全部丢失。生成尚未结束时，应标明集合尚未完成，完整批准导出保持关闭。

### 三层质量校验

| 层次 | 检查 | 谁决定 |
| --- | --- | --- |
| 结构 | 类型、必填项、步骤编号、ID 唯一、完整响应 | Pydantic/代码 |
| 引用与一致性 | 版本存在、对象归属、需求关系、状态、约束冲突 | 代码与结构化规则 |
| 语义 | 来源是否支持预期、是否漏关键条件、是否捏造权限 | 证据复核模型建议 + 人工确认 |

当前 coverage_report 是关联覆盖：若模型漏抽需求，该需求不会进入分母。生产展示必须区分“已识别需求的关联覆盖”和“人工确认需求的语义覆盖”；ID 存在不能证明引用正确。

Google 提供 JSON Schema 结构化输出能力；应在 Provider 协议增加能力声明，支持时提交小而明确的阶段 Schema，同时保留服务端校验、拒答和截断处理。当前 json_object 模式不能替代业务正确性验证。[Google 结构化输出文档](https://ai.google.dev/gemini-api/docs/structured-output)

## 4. 两个最有价值的真实业务闭环

### 澄清答复转需求修订

当前澄清主要支持误报或非阻断处理，新增业务事实需要修改 PRD。建议增加：问题 → 用户答复 → 需求补充提案 → 授权人员确认 → 新需求版本 → 受影响用例修订。

例如原文只写“金额大于 5,000 元需要二级审批”，没有写一级审批人。系统可生成明确阈值相关的草稿，同时提出审批人问题；不能把“财务主管”直接作为事实。用户回答“直属主管”后，团队内按需求确认权限形成正式补充，再生成依赖该角色的可执行用例。个人空间由本人确认。

人工退回理由也不自动成为新规则：“改成超过 3,000 就二审”与原文冲突时，修订 Agent 应提出需求变更，不直接修改预期后声明已修好。

### PRD 更新后的影响分析

当阈值从“大于 5,000”变为“大于等于 5,000”时，系统需要：

1. 标识比较运算符发生变化，保留两版原文。
2. 定位关联边界、审批路径和权限用例；边界测试值须使用已明确的金额单位和精度。
3. 为受影响用例生成修改提案和差异，重新审核。
4. 无影响用例仅在内容、依赖及审批策略均满足复用条件时沿用批准，并记录依据。
5. 无法可靠判断影响范围时标记待复核，不能以“未检索到关联”推断无影响。
6. 历史批准导出保持原样，新需求版本产生新基线。

这比每次上传 PRD 都重新生成一个孤立批次更有长期使用价值。

## 5. 数据模型与状态机

保留现有运行快照、审批事件和导出记录，增量引入：

| 对象 | 关键字段/作用 |
| --- | --- |
| document / document_revision | workspace、project、稳定文档 ID、版本、来源、哈希 |
| source_block | 版本、块 ID、标题路径、原文 span/quote、内容哈希 |
| requirement / requirement_revision | 稳定规则 ID、版本、约束、状态、来源 |
| case / case_revision | 稳定用例 ID、版本、内容、内容哈希、审核状态 |
| trace_link | 用例版本与需求版本的关系及证据；支持多对多 |
| clarification / answer | 问题、影响范围、答复、确认人、确认版本 |
| change_set | 新旧需求差异、受影响对象、确认结果 |
| workflow_run / step_run / attempt | 输入版本、状态、租约、尝试号、输出引用、耗时 |
| tool_call | 工具版本、可信授权上下文引用、参数摘要、结果引用 |
| review_event / baseline / export | 具体版本批准、范围清单、导出快照 |

当前 P001 等编号适合在一次运行中展示；跨版本锚点建议使用 document_revision_id + block_id + quote/span + hash。稳定实体 ID 和版本 ID 分开；hash 用于完整性校验，不能独自解决跨版本身份映射。

工作流状态可包括 queued、running、waiting_for_user、partially_ready、completed、failed、cancel_requested、cancelled；用例状态独立包括 draft、needs_clarification、pending_review、approved、returned、superseded。不能用一个 failed 同时表示供应商超时、版本冲突、结构错误和待澄清。

记录每一步的输入/输出引用、工具调用、简短决策摘要和依据，足够进行故障排查；不以存储模型私有思维链为追溯要求。相同参数重跑也不保证模型逐字一致，可复核性主要来自原始响应、版本、依据与事件。

## 6. 项目知识与记忆

先实现当前文档、已确认需求、授权历史批准用例的结构化检索；资料规模和召回质量证明需要时，再加入向量检索。候选技术可在 PostgreSQL 内补全文/向量能力，避免一开始额外维护多套数据库。

检索前按 workspace、project、访问权限和有效版本过滤，再做排序；检索后仍校验对象权限。不能先全租户检索再在显示时过滤。缓存键也必须带租户、项目、版本与授权范围，权限撤销和版本变更需要失效策略。

记忆分为：任务短期状态、项目已确认规则、用户展示偏好。未批准草稿和随意反馈不能直接变成长期业务事实。长期规则记录作者、确认人、适用范围、版本与失效时间。来源发生冲突时提出问题，由有权人员决策，不默认“最新文档必然正确”。

## 7. 推荐工程架构

建议从模块化单体出发：浏览器 → HTTPS 网关 → 业务 API → PostgreSQL；独立 Worker 读取持久任务并调用模型；原文、附件、导出保存在私有对象存储。

- API：复用现有 Starlette 认证与业务语义；按需要引入 FastAPI 提供类型化 API/OpenAPI，不为框架名重写业务。
- 前端：Streamlit 可维持受控试点。面向长期多人产品，逐步迁移为 TypeScript + React 类前端，以稳定组件、路由和状态管理实现审核表格、差异对比和任务通知。
- 工作流：先明确自有状态与事件协议。若选择 LangGraph，使用持久 checkpointer 支持中断与恢复；任务队列负责分派和租约，图负责单次流程，不形成两套相互矛盾的业务状态。简单有限状态机也可以实现第一版。
- 数据：PostgreSQL + 版本化迁移；私有对象存储保存大内容。Redis 在需要共享高频限流/缓存时再引入。
- 部署：API 与 Worker 分离进程和资源限额，使用托管数据库/对象存储及可重复构建的容器。初期无需微服务拆分或 Kubernetes。

LangGraph 的 checkpointer 可以保存流程状态，interrupt 支持等待外部输入；内存 checkpointer 无法跨重启恢复。恢复时中断节点可能从头运行，因此副作用必须幂等。框架持久化不替代业务权限、审批和数据库事务。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[人工中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

Streamlit 多副本涉及 WebSocket 会话及上传/媒体等请求的会话亲和问题；简单复制现有进程不能完成生产扩容。[Streamlit 架构说明](https://docs.streamlit.io/develop/concepts/architecture/architecture)

## 8. 可靠任务、并发与费用

### 任务可靠性

在同一事务创建工作流与任务，API 返回任务 ID。Worker 通过原子领取、租约、心跳管理执行；每阶段提交产物和检查点，进程崩溃后恢复未完成步骤。若未来改用外部队列，使用 outbox 等方式避免数据库已写而消息未发送。

每次尝试有唯一 ID，结果提交带 expected_revision 和终态检查；重复投递不重复生效，迟到结果不能覆盖人工修改或取消结果。任务按至少一次执行设计，外部模型请求不承诺恰好一次，也不能保证绝不重复计费。

429/临时 5xx 可以按 Retry-After、指数退避和抖动进行有限重试；鉴权失败、参数错误不盲重试。网络超时可能意味着供应商已完成但结果未知，需单独记录该状态并按策略处理。

取消排队任务可直接停止；执行中的取消只能保证不再推进/发布结果，不能承诺供应商停止计费。用户退出登录通常不必取消已经授权的任务；成员被移除、项目归档或权限撤销时应在关键执行/提交点重新检查。具体政策必须显式实现，不能由浏览器 Cookie 是否过期偶然决定。

### 数据一致性

SQLite 当前依靠 BEGIN IMMEDIATE 串行化写入。迁移 PostgreSQL 时，审批、编辑、导出须改成行锁或带 revision/status 条件的更新，并检查影响行数；不能只换连接字符串。版本冲突返回可解释的冲突结果，展示最新差异。

导出固定基线范围与版本清单。若以后支持范围导出，用户须明确选择范围，并披露排除项和覆盖缺口；不能通过静默删掉退回用例让整批变成“全部通过”。

### 容量与预算

将在线浏览人数、提交任务速率、模型调用并发、Token 吞吐和数据库读写分别测量。若每分钟 12 份 PRD、每份平均 6 次模型调用、每次平均 30 秒，则需求约 72 次调用/分钟、稳态约 36 次在途调用；尚未计重试和峰值。这只是计算示例，不能当作当前容量。

当前基础 admission 计数不等于真实模型调用次数。应为 workspace/user/provider 设置活跃任务数、队列长度、最长等待、RPM/TPM、Token/金额预算；开始前原子预留，返回后结算，未知用量单列。按租户公平调度，避免一个大团队占满所有 Worker。队列满时快速提示稍后重试。

Google 限流按项目而非 API key 计算，并有 RPM、输入 TPM、RPD 等维度。增加同一项目的密钥不会解决项目配额瓶颈；生产参数以实际账号与模型限制为准。[Gemini 限流说明](https://ai.google.dev/gemini-api/docs/rate-limits)

## 9. 安全与数据治理

1. **身份与权限**：保留现有服务端 RBAC 和对象授权；按试点需求增加项目可见范围、账号恢复、会话管理、管理员 MFA。团队可配置审核人/编辑人分离，个人模式允许本人审核。管理员也不能跳过版本和完整性门禁。
2. **Agent 边界**：当前 providers.py 将完整 rendered PRD 作为 system 消息发送。应拆分可信系统指令、用户任务和不可信文档内容；分层只是减轻风险，工具授权与输出处理才是实际边界。对 PRD、检索片段、用户反馈和工具结果都按不可信内容处理。
3. **租户隔离**：业务数据、文档块、检索索引、附件、缓存、任务、日志与下载均绑定空间。RLS 可作为 PostgreSQL 纵深防护；应用角色不应拥有绕过权限，连接池设置/清理租户上下文需有测试，不能只加一条 policy 就宣称隔离完成。
4. **生产配置**：HTTPS、Secure/HttpOnly Cookie、可信 Host/代理、CSRF、合理安全响应头、接口限流；模型与连接器出口地址白名单，保护内网和云元数据地址。若增加 URL 导入，还需针对 SSRF、跳转和 DNS 变化做专门防护。
5. **密钥**：为 TraceCase 建独立服务商项目与预算，开发/测试/生产分离，使用部署平台 Secret Manager；不在生产复用桌宠凭据，不在模型工具里暴露密钥。
6. **数据生命周期**：原始 PRD、渲染 Prompt、模型输出、审核意见与导出都可能敏感。存储与备份加密，日志默认不记正文；定义保留、删除、脱敏和备份过期策略。区分最小审计事件和可删除业务内容。
7. **审计**：现有不可变触发器保护普通应用写入，不防数据库管理员。按客户要求再增加独立只追加审计落点和管理操作审计，不把现有追溯称为监管认证。

OWASP 将工具功能过多、权限过大、自主性过强列为过度代理风险来源。TraceCase 的权限边界应让模型即使被恶意 PRD 误导，也无法批准、越权读取或修改成员权限。[OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/?lang=us)

PostgreSQL RLS 有角色与表所有者绕过等注意点，应结合应用授权而不是替代它。[PostgreSQL 行安全文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

### 当前免费 Gemini 接入的生产决策

Google 当前条款对 Unpaid Services 说明输入和输出可能用于产品改进，并可能由人工处理，同时要求不要提交敏感、机密或个人信息；EEA、瑞士和英国存在条款例外。付费服务的数据使用规则不同，但也不能推导为零保留。是否属于 Paid Services 需依据实际 Cloud Project/Billing 状态核实，不能仅根据“拿到了 API key”判断。接收真实公司 PRD 前，需确定数据分类、供应商协议与允许的使用方式。[Gemini API 条款](https://ai.google.dev/gemini-api/terms)

同时确认部署地域与目标用户访问条件，按供应商支持地区选择服务，不能把本机能调用当作生产可用证明。[支持地区](https://ai.google.dev/gemini-api/docs/available-regions)

## 10. 评测：证明 Agent 的增量

保留现有 fixture 作为回归资产，但不计作真实模型能力证据。现有 20 份报销材料仍是待人工确认的候选标准，CLI 也没有正式模型执行器。

第一批建议建立 30–50 份经授权脱敏或人工精心构造的多样文档，再扩到 100 份以上；这是采集目标，不是当前样本量。按项目/来源家族划分开发与固定留出集，避免同一 PRD 改写版本泄漏到两边。统一应用与评测的 Markdown 解析器及版本。

三组对照：A 当前单次生成；B 分阶段确定性工作流；C 增加检索、缺口修复和反思的受限 Agent。同一模型/参数/语料下先比较预算匹配结果，再单列放宽预算后的成本质量曲线。重复运行用于观察波动，不能把同文档的重复运行当作完全独立样本夸大统计把握。

| 指标 | 建议定义 |
| --- | --- |
| 首次 Schema 合法率 | 首次响应无需修复即通过结构检查的任务/任务总数 |
| 修复后可审核率 | 明确区分全量可审核与部分可审核；记录各自分母 |
| 需求覆盖率 | 人工标准中必测条件全部正确覆盖的规则数/标准规则总数 |
| 无依据断言率 | 无原文或已确认补充支持的业务断言数/抽样业务断言总数 |
| 可执行率 | 测试人员能准备前置条件、执行并判断预期的用例数/审核用例总数 |
| 澄清质量 | 应澄清项召回率与提出问题的准确率，分开统计 |
| 人工负担 | 首次审核时间、修改时间、返工轮数、最终有效用例数 |
| 成本与延迟 | 排队、各阶段、总时长 P50/P95；每个有效批准用例的实际模型费用 |
| Agent 控制 | 非法工具调用被拦截、循环终止、恢复成功、越权结果未生效 |

评测必须覆盖长文、表格、跨章节定义、冲突阈值、未知权限、状态机、幂等、外部依赖、多版本和提示注入。语义指标由人工标准判定；另一个 LLM 的分数只作辅助。真实用户“点通过”是行为信号，不直接等于正确答案。

冻结后保留原始结果、人工标注、模型及 Prompt/Schema/解析器/检索/工具版本。用户界面仍保持一个通用入口，内部版本管理不必暴露为用户选择。

## 11. 交付、运维与上线准入

沿用现有 CI，再补充：类型检查、依赖/密钥扫描、数据库迁移校验、API 合约、PostgreSQL 集成测试、关键浏览器端到端测试、构建产物和预发布烟测。使用 Issue → 分支 → 提交 → PR，将验收标准写入 Issue；当前没有配置 Git remote，不应把本地提交描述为已经完成远端协作。

可观测性将 request_id、workspace_id、workflow_id、step_id、attempt_id 关联起来，采集队列等待、模型延迟、429、失败原因、预算、审批冲突和导出失败。日志与 Trace 默认不记录 PRD 正文；受控调试原文单独授权。OpenTelemetry 可统一 traces、metrics、logs。[OpenTelemetry 信号](https://opentelemetry.io/docs/concepts/signals/)

以下是首次受控团队试点的建议验收，需在目标部署环境实测，不是当前达标声明：

| 领域 | 必须证明 |
| --- | --- |
| 隔离 | 跨团队 ID、检索、下载、任务和缓存访问均被拒绝；移除成员后不能继续读写 |
| 可靠性 | Worker 被终止后恢复；重复投递不重复生效；取消后的迟到响应不发布 |
| 并发 | 编辑/审批/导出竞争不覆盖新版本；冲突有明确反馈 |
| 模型故障 | 429、超时、无效 JSON、截断、拒答和预算耗尽均有可恢复状态 |
| 长文档 | 单批失败保留其他结果，重试不重做成功批次 |
| 注入 | 恶意 PRD 不能改变权限、读取其他项目、批准或发起任意外部请求 |
| 数据恢复 | 实际从备份恢复账号、需求、审批和导出；核对关联一致性 |
| 质量 | 固定留出集无明显退化，关键规则漏检单列；报告人工审核耗时与成本 |
| 部署 | 数据迁移演练、版本回滚/前向修复、健康检查和告警可用 |

可先拟定试点目标：非模型交互 API 在约定负载下 P95 < 500 ms、任务持久入队 P95 < 1 s；备份 RPO ≤ 15 分钟、恢复 RTO ≤ 60 分钟。并发规模、可用性窗口与生成延迟目标须根据部署预算和真实文档长度另定。压测分为模拟供应商的系统容量测试与小规模真实模型验证，不能用昂贵 API 请求盲目堆负载。

## 12. 分阶段落地与验收成果

下表为依赖顺序与粗略迭代估算。假设一名熟悉现有代码的全职工程师、能及时获得产品/测试人员反馈、使用托管基础设施；不是交付承诺，身份、采购和真实数据准备可能成为关键路径。

| 阶段 | 参考时间 | 范围 | 验收产物 |
| --- | --- | --- | --- |
| A 基线与契约 | 1–2 周 | 试点场景、现状文档、人工标准、真实评测执行器、状态/API契约 | 可复现基线报告、首批冻结标准、迁移设计 |
| B 可靠后端 | 2–3 周 | PostgreSQL、独立 Worker、租约恢复、幂等、权限主体、预算、备份 | 断进程恢复、权限撤销和并发冲突演练通过 |
| C 分阶段生成 | 2–3 周 | 版本化证据、规则抽取、覆盖计划、分批生成、局部修复、阶段进度 | 复杂 PRD 部分成功与续跑；质量/成本对照 |
| D 受限 Agent 与需求变更 | 2–3 周 | 工具边界、证据检索、缺口修复、澄清转需求、影响分析、差异审核 | 两个关键闭环及攻击/预算终止评测 |
| E 受控上线 | 1–2 周起 | 正式供应商配置、监控、容量、安全、试点反馈、发布回滚 | 准入报告、运行手册、恢复记录、真实使用反馈 |

前端迁移可在 API 契约稳定后分模块进行，单独估时；不要把整站重写隐含在上表里。阶段 E 的安全和运维工作应从 A/B 开始建设，不能等最后才检查。

建议最先建立的工程 Issue：

1. 更新当前架构事实并定义试点范围与准入条件。
2. 建立统一解析器和实际模型评测执行器，冻结首批人工标准。
3. 抽取 repository/事务边界，迁移 PostgreSQL 并验证审批并发。
4. 拆分独立 Worker，增加租约、恢复、取消与任务主体授权。
5. 增加工作流/阶段/尝试账本与真实进度事件。
6. 文档版本、稳定证据、需求关系及用例跨运行身份。
7. 模块化生成、部分成功、三层校验和局部修复。
8. 澄清确认、需求变更影响及差异复审。
9. Agent 工具白名单、预算控制、项目检索及注入评测。
10. 生产配置、密钥/数据策略、可观测性、备份恢复与受控试点。

优先保留：可信身份、权限边界、审批事件、旧版本、导出快照、Provider 抽象和已有回归测试。暂缓：全自治多 Agent、任意代码执行、大规模微服务、提前微调、没有收益证据的复杂向量体系。每一项复杂度都应对应实际用户问题和可测量收益。

Agent 与工作流的区别及逐步增加复杂度的原则可参考 [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。本文具体流程、选型组合和优先级是结合 TraceCase 代码作出的工程建议，不是来源对本项目的验证结论。
